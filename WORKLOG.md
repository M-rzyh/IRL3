| 2026-07-09 | **CONCEPT: how game speed actually works (why `time.sleep` is there).** The simulator has **no clock**. `env.step()` is arithmetic (~0.07 ms); the `FPS = 50` constant only says *how much game time one step represents* (dt = 1/50 s) — it does **not** make the call take 20 ms. Two clocks: **game time** = `steps × 1/50` (fixed, exists even if you never draw a pixel); **wall time** = how long a human actually sits there (we choose it). **Real time ⇔ wall == game.** Left unthrottled, step+render+JPEG ≈ 2.7 ms/step, so 100 steps (= 2.0 s of game time) compute in 0.27 s → the lander would fly at **~7× real time**, correct but unflyable. `human_demo.py:454` `time.sleep(1.0/fps)` is the throttle that makes it human-speed: sleeping 40 ms/step ⇒ 25 steps/s ⇒ `--fps 25` ⇒ 0.5× real time. **The sleep IS the fps.** Gym's own `render_mode="human"` does the same job via `clock.tick(metadata["render_fps"]) = clock.tick(50)`. **Why we don't use it:** it opens a pygame window on the compute node (headless; the human plays through an SSH tunnel + browser), so frames must be `rgb_array` → JPEG → HTTP and keys must come back the same way; also `clock.tick` is pinned to 50, giving no slow-down knob. Architecture is sound; two defects remain: (1) `clock.tick` sleeps to a **deadline**, ours sleeps a **fixed pad after** the work, so each step costs `overhead + 1/fps` → 25 requested vs 22.6 achieved (**~10% shortfall**, and *not constant*: a blanked frame is 4 KB of JPEG vs 196 KB, so blanked steps run faster); (2) the fps is never recorded. Fix = `sleep(max(0, 1.0/fps - elapsed))` + `session_meta.json`. `human_demo.py` predates this work (initial commit `0ab99b0`); only the `--blank-*`/`--region-*` flags were added by us. PT's side of this (no sleep; fps stamped into the MP4 header) is in the PT WORKLOG. | Recurring confusion: "shouldn't 100 steps take 2 s?" No — only if something waits 20 ms per step. Nothing does, unless we make it. |
